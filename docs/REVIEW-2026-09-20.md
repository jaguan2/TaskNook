# Functionality review — September 20, 2026

This 20-minute review focused on task persistence, chat history and delivery,
database queries, and migration coverage. Existing room/panel changes were
preserved. No commits or pushes were made by the review.

The chat pagination endpoint remains compatible with existing clients: no
`before` parameter returns the usual newest page as an array. A `before`
message ID must belong to the requested conversation. Pages use timestamp and
ID together, so identical timestamps do not duplicate or skip messages.

No database schema changes or new runtime dependencies were needed.

## Remaining opportunities

These are findings from source inspection, not features implemented in this pass.

1. **Preserve routine completion history.** `backend/app.py::list_tasks` clears
   yesterday's routine `completed_at`; `CalendarPanel.jsx` builds its Completed
   journal from that same field. Yesterday's routine completion consequently
   disappears after the daily reset. A separate completion-history table would
   preserve each day's achievement while the standing task resets. This needs
   a migration and an explicit policy for undoing a completion.
2. **Make pending bot replies survive an app restart.** Reply timers in
   `store.jsx` survive closing the drawer, but are memory-only and are cleared
   on provider unmount. A failed reply write is also silently dropped. A durable
   queue with a stable message identifier would support restart/retry without
   duplicating a reply when a request times out after SQLite already saved it.
3. **Tie read receipts to the transcript actually displayed.** The read endpoint
   stamps server “now,” after the transcript fetch. A message arriving between
   those requests can be counted as read before it was displayed. Passing a
   last-seen message cursor and storing it on membership would close that race;
   the existing timestamp-only model also needs a tie policy.
4. **Edit/reschedule calendar appointments.** Appointments currently have create,
   list, and delete paths, but no edit route or editor. Changing the time requires
   deleting and recreating the appointment. Add a partial update with the same
   date/time validation and an inline editor.
5. **Complete account-deletion cascades if account management is added.**
   `CalendarEvent.user_id` has a foreign key, but `User` lacks the delete-orphan
   relationship supplied for tasks, sessions, tokens, memberships, and messages.
   There is no account-delete UI/API today, so this is a future model consistency
   gap rather than a currently exposed user workflow.

Furniture and character registries, preset geometry, and sprite rendering were
covered by the existing automated tests. No new visual-model defect was
confirmed and no artwork was changed. A screenshot review remains useful for
silhouette/occlusion issues that registry and render tests cannot establish.
