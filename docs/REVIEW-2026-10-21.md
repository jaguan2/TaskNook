protects upgrades; migration tests cover data preservation and rollback.

## Chat performance checks

The reviewer ran real loopback HTTP against baseline/current routes on the
same disposable **12-thread, 100,000-message** SQLite fixture. Authentication,
ORM loading and JSON serialization are included; setup/index creation are not.
Each endpoint used three warmups and fifteen samples. No test suite or build
ran during sampling. One counterbalanced repeat investigated the first run's
deep-page slowdown; no further repeats were made.

| Endpoint | Old→new median, old phase first | Old→new median, new phase first |
| --- | ---: | ---: |
| Latest 200 messages | 15.296→14.681 ms | 34.283→3.327 ms |
| Deep 200 messages | 8.784→12.348 ms | 18.325→13.582 ms |
| Thread list | 158.047→40.535 ms | 315.412→40.874 ms |

Thread-list improvement is consistent and meaningful. Page HTTP timings vary;
these measurements do not establish a general pagination-response speedup.
The initial deep-page slowdown did not persist in the counterbalanced run.
Actual history plans use the composite index without a sort, and deep pages
seek to the timestamp boundary. Reverse-run database execution medians were
25.311→0.241 ms for latest pages and 10.405→0.334 ms for deep pages, excluding
row fetching/ORM work. Unread aggregation still scans relevant history; thread
lists are not constant-time.

Exact history payloads/IDs, thread payloads, independently calculated unread
counts, outsider membership refusals and foreign/invalid cursor handling all
matched. Evidence: `chat_endpoints.py`, `chat-endpoints-results.json` and
`chat-endpoints-new-first-results.json` in the ignored verification directory.
The fixture was removed after each run. These are local synthetic measurements,
not native WebView2 performance or measurements of the owner's database.
